# Easy Ask AI

**想法说不完整，AI 帮你问清楚；作品不满意，问明白再动手改。**

Easy Ask AI 包含两个可独立使用的 Skill。**Prompt Ready** 在开始前梳理需求、生成详细执行提示词；**Get Clear** 在收到“AI味重、不满意、不好看、不够高级”等模糊反馈时，逐条追问期望，确认后继续当前任务的实际返修。用户不用先学会设计术语，也不用独自写出完整规格。

## 安装与开始使用

需要能读取 Skill 和任务文件的 Agent 宿主。从 [GitHub Releases](https://github.com/Ww-Cooooo/easy-ask-ai/releases) 下载完整套件，解压后将 `skills/` 下需要的完整 Skill 文件夹复制到当前宿主实际确认的技能目录；可以只安装其中一项。保留参考文件、脚本及许可证，不要只复制 `SKILL.md`，也不要把套件根目录当成单个 Skill 安装。已有同名目录时先核对来源和本地修改、做好备份，再合并更新。

Skill 路径、显式调用方式和持久规则载体都由宿主及版本决定，本套件不假设统一接口。可以把完整套件或单个 Skill 目录交给安装 Agent，并使用[通用接入指南](docs/host-integration.md)中的启动指令。这给尚未安装或尚未被宿主发现的 Skill 提供了可找到的起点；它要求 Agent 从用户提供的本机目录开始读取，Skill 不会在后台自行启动。

是否接入用户级或项目级持久规则由用户授权范围决定；只安装不改规则也是受支持的选择。每个 Skill 包都附有通用宿主调查、规则合并、刷新、新会话核验、短记录和撤销说明，以及供 Agent 读取的可选规则片段：[Prompt Ready](skills/prompt-ready/references/host-integration.md)、[Get Clear](skills/get-clear/references/host-integration.md)。首次明确业务调用只做轻量状态核对，不因宿主诊断延迟明确的小改；普通调用不授权写入全局规则。

此前在 Codex、官方 DeepSeek Harness 等环境留下的检查记录只支持其所述实例和状态，不是宿主允许名单、当前路径保证或自动选择证明。验证时分开记录 Skill 已安装、宿主已发现、规则已写入、宿主已加载、模型已读入口、正常业务行为通过和用户已接受；未验证项如实标明。[验证记录](VALIDATION.md)区分本轮检查和历史结论；通用接入与排查入口见[docs/integration.md](docs/integration.md)。

首次进入准备或反馈访谈流程时会检查 `grilling` 和 `more-than-yes`。缺失时，Agent 在当前授权和宿主权限内从固定 GitHub 版本下载、审阅后补装，保留已有有效安装。Get Clear 的明确修改分支跳过访谈与这两项依赖准备。辅助脚本需要 Python 3.10+；没有 Python 时可使用宿主已有安装和编辑能力。详见 [依赖说明](skills/get-clear/references/dependencies.md)。

## 为什么做这套工具

我平时经常使用轻量模型。一个实际感受是：只用一句话描述想法，让模型直接开工，很难稳定得到符合预期的结果。

这种“许愿式编程”把太多事情留给了模型临场判断：用户究竟想解决什么问题、有哪些没说出来的限制、应该采用什么方案、做到什么程度才算完成。换成写课程、做内容或整理业务流程，同样会遇到这些问题。

因此，我更希望先让模型担任技术监督：把需求问透，调查已有条件，补齐方案，再写出足够详细的执行 Prompt，交给新对话里的模型实施。可以用较强模型负责准备，也可以让同一个模型分两次对话完成准备和执行。

但困难不只发生在开始前。看到第一版后，用户常常只能说“不够好看”“不够高大上”。这是确实不满意，却还没有说明应该怎样改。用户脑中可能也只有一个模糊印象，无法逐项指出字体、构图、节奏或交互的问题。

如果 AI 此时自行把“高级”解释成某种配色、更多动画或另一套布局，很容易沿着错误方向反复制作。不断要求用户“说具体一点”也没有帮助；AI 应当结合当前作品，提出用户能够回答、答案又确实会改变设计的问题，帮助双方逐步弄清目标。

Easy Ask AI 把这两段协作做成可重复使用的流程。它不会用更长的问卷代替判断，也不要求用户承担专业设计工作。

## Prompt Ready：先把任务准备完整

1. 调用 **grilling**，根据任务和回答深入追问，弄清用途、完整过程、交付物、限制及验收标准。
2. 调用 **more-than-yes**，检查前提、资源、遗漏和取舍。会改变结果、成本或使用方式的建议，回来确认。
3. 结合真实项目与材料，写出包含所有阶段、操作步骤、输入输出、质量检查和失败处理的详细执行 Prompt。
4. 当前准备者保存并回读需求、执行 Prompt 和启动指令，核对事实、计算与连续操作场景；发现稿件错误就自行修正、复核，完成后才提供启动指令。**同一工作区的新对话**负责执行任务，不是让用户另外开一个对话替准备稿纠错。

默认在 `.prompt-ready/<任务名>/` 保存 `requirements.md`、`execution-prompt.md` 和 `start.txt`。打开 `start.txt`，复制其中的完整指令到同一工作区的新对话；新对话先核对工作区和材料，再执行。它默认不代开对话，也不在准备阶段开始制作。

已有的 `$prompt-ready` 名称与输出路径保留，旧任务可以继续。[完整说明](skills/prompt-ready/README.md) · [虚构交接示例](skills/prompt-ready/examples/library-book-swap.md)

## Get Clear：把不满意问清楚，再继续做

Get Clear 面向已有成果的模糊返修，适用于网页、视频、文案、产品和业务方案等任务。“好点了，但还是不对”仍有待解决的分歧；即使用户建议参考某种做法，也要先确认想改变的体验，不能直接把方案换成参考案例。

- **先看作品和上下文。** 区分观察到的问题、用户的感受与模型的猜测。
- **复述时不偷换用途。** 保留用户所指的人、行动和所处阶段；会导致不同改法的解释先辨清，再询问对应材料。
- **调用 grilling，一次问一个主要问题。** 问题中带上现稿的句子或作品里的具体表现。用户说不清时，用容易比较的短例帮助辨认，不要求用户先找到参考或自行分析原因。
- **问到整体方向和关键边界明确。** 不设固定题数，不因问清一个局部就结束，也不以“先做个小样”为由绕过尚未明确的意图。
- **调用 more-than-yes 检查遗漏。** 核对解释、取舍、已接受内容与可实现性，再复述修改方向，请用户确认。
- **在当前任务执行返修。** 使用相应领域工具完成修改，对照真实成果检查，不默认让用户换窗口，也不只交一份建议。

例如，用户说一个报名页“没档次”，问题可能是促销感太重，也可能是没有体现活动本身的吸引力。Agent 需要结合页面帮助用户区分；即使知道“不想像促销”，仍要进一步弄清希望带来的感受、必须保留的信息以及明确拒绝的方向。[网页访谈](skills/get-clear/examples/landing-page.md) · [用户仍说不清时怎样继续](skills/get-clear/examples/unclear-copy.md)，均为虚构教学示例。

明确修改直接进入短执行分支，例如“只把标题换成这一句，其他不动”：当前回合实际保存并核验，精确替换还要保留无关内容、编码和换行；包内提供仅依赖 Python 标准库的替换工具。用户已经确认的答案不重问。目标是帮助表达并完成工作，不能要求用户证明自己的偏好，也不能保证读懂脑中所有画面。

## 旧版本与接入

本套件由 Prompt Ready 扩展而来。Get Clear 是重新设计的返修技能，不依赖 Clear Feedback，也不把它作为兼容入口。用户若希望替换旧安装，应移除旧技能的活动入口，并把自己项目规则中指向旧技能的调用改为 `get-clear`。已有聊天可能仍持有旧清单，需要刷新或新开对话。

技能的描述和调用规则能够指导 Agent，不能在所有宿主中强制拦截编辑。验证时分别查看：是否发现、是否主动读取、是否先澄清，以及最终是否达到要求。[接入与排查](docs/integration.md) · [验证范围](VALIDATION.md)

## 文件、依赖与许可

业务材料和需求记录保存在当前工作区；技能不自带读取全部历史聊天或上传作品的程序。Agent 和业务工具的数据处理遵循各宿主规则。依赖辅助脚本只请求锁定的公开 GitHub 包，不读取凭据、不上传任务文件、不执行下载内容，安装前需 Agent 审阅。

维护者可从仓库根目录运行：

```text
python -X utf8 -m unittest discover -s skills/prompt-ready/tests -v
python -X utf8 -m unittest discover -s skills/get-clear/tests -v
```

这些测试分别检查依赖安装边界与精确替换工具，不能代替技能触发或业务效果验证。详细 Prompt 和访谈也不能消除模型能力差距。
