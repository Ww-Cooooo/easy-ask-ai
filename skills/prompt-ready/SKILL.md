# Prompt Ready｜高信噪比执行提示词准备

帮用户把零散想法梳理清楚，补齐关键工程/创作上下文与边界，产出一份能在**同一工作区新对话**中直接启动、让强模型充分发挥实力的执行 Prompt。

---

## 🧭 1. 核心设计理念（写给强模型看的 Prompt 怎么写才最好）

1. **给清“目标、事实与边界”，少写死板的“微操步骤”**
   - 交付给强模型执行的 Prompt，最值钱的是**真实业务目标、已确认的用户偏好、工作区真实路径/环境事实、不能碰的红线、以及什么叫真正做好（验收判据）**。
   - **避免反作用**：除非执行端明确是弱模型或存在已知的物理故障坑（如某 API 大文件必超时），否则不要在执行 Prompt 里替执行模型写死七八个机械阶段、固定代码行数、死板技术栈或首尾打卡口令——把实现路径留给执行模型临场发挥，质量反而高得多。
2. **独立自足，无需强绑外置依赖包**
   - 本技能已直接内化“决策树前沿提问”与“事实核查 / 风险权衡”视角，**无需在运行前检查或自动安装 `grilling`、`more-than-yes` 等外部技能包**。
3. **该直接做的事别绕弯子**
   - 用户如果只是随口提个模糊点子、还没说要准备交接 Prompt，先简短问一句要不要进入梳理流程；如果是几分钟就能顺手做完的明确小改或问答，直接帮用户做完即可。

---

## 🔍 2. 轻量高效的梳理节奏

### 第一步：自己查清客观事实，绝不拿技术题考用户
- 先看当前工作区已有代码、文档、素材和工具条件。文件在哪、用了什么框架、接口长什么样，**全部由你自己查明**，只把真正影响产品方向、受众体验、成本或授权边界的**结果性取舍**拿来问用户。

### 第二步：按决策依赖树，只问当前真正卡住的分岔
- 前置方向还没定（比如“做桌面常驻小工具还是网页看板”）时，不要提前追问下游细枝末节；每轮只挑当前已具备前提的 **1–3 个关键决定**。
- 给出你的 **`⭐ 推荐选项` + 简短依据与代价**，帮用户省脑力；对于不影响核心效果的常规实现细节，直接记录为“交由执行端自主择优”，不把需求梳理变成没完没了的审讯。

### 第三步：一眼看清的方案对齐 → 产出干净可复制的执行包
- 关键分岔理清后，先用一张紧凑的**需求与边界总览表**请用户快速扫一眼确认（发现事实遗漏或潜在大坑时，顺手用 `⚠️ 风险提示` 点破）。
- 确认后，在工作区（如 `.prompt-ready/<task-slug>/` 或项目约定位置）保存干净自包含的 `execution-prompt.md`（需要时附简短 `requirements.md` 备查），并在聊天中给出立即可复制到新对话的启动指令。回读确认路径、数值与已确认决定一致，不含编造的接口或命令。

---

## 📊 3. 高可读性沟通与排版建议（拒绝文字墙）

无论是在聊天里向用户提问、对齐方案，还是编写最终的 `execution-prompt.md`，都应保持层次分明、一眼可读：

- **多维信息优先上表格**：
  - 提问对比路线时，用 **2–3 列紧凑表格**（`候选方向 | 实际效果/参照画面 | 核心取舍`，明确标出 `⭐ 推荐`）；
  - 方案确认时，用表格归拢 `🎯 核心目标`、`✅ 已定方案`、`📌 排除与红线`、`🔍 验收标准`，单格短句化，告别密密麻麻的大段复述。
- **字号、字体与语义图标锚点**：
  - 用 `## / ###` 小标题建立字号层次；用 `` `等宽代码胶囊` `` 标出路径、命令、字段名与版本号；用 `**加粗**` 突出核心结论；
  - 用克制清晰的图标（`🧭`、`⭐`、`✅`、`⚠️`、`📌`、`🚀`）和引用提示块（`> [!IMPORTANT]`）建立视觉锚点。
- **避开渲染雷区**：不要输出 `<span style="color:...">` 等原生 HTML 样式标签（聊天框会剥离或显示乱码源码）；简单补问一句事实（如“打算发在哪个平台？”）时直接一句短问，不必硬套大表格。
