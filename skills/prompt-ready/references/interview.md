# 深入访谈的方法

## 建立问题树，而不是一张问卷

先把任务拆成相互依赖的决定。例如课程：学员与目标 → 真实学习困难 → 教学活动 → 练习与评价 → 内容组织。先确定学员才能问练习难度；封面颜色通常不必占据第一轮。

每个分支只记录有用的信息：问题、为什么会改变结果、前置条件、已知依据、答案或委托状态。工作记录是续接材料，不要求用户读一张复杂管理表。

沿着用户叙述走一遍具体场景：“一个人从什么状态开始，经过哪些动作，看见什么结果？”然后检查会改变设计的反例、失败和边界。不要穷举不存在的场景。领域新颖时，从实际过程推导问题，不强套软件开发术语。

把模糊词转为可比较的结果：

| 用户说法 | 应继续确认的内容 | 不该直接推定 |
| --- | --- | --- |
| 做得专业一点 | 面向谁、使用场景、参考中喜欢哪些特征、哪些表现不能接受 | 深色界面、更多动画就专业 |
| 自动整理资料 | 哪些来源、按什么目的分类、是否改名/移动原件、冲突怎样处理 | 可以遍历整块磁盘并删除重复文件 |
| 做一门有用的课 | 学员起点、结课能完成的任务、学习时间、如何练习和评价 | 固定十课时和一份 PPT |
| 给我研究清楚 | 要支持哪个决定、范围与时间、证据要求、如何呈现不确定 | 联网摘要拼成长文就是完成 |

## 每轮怎么问

读取 `grilling` 的方法，列出当前所有前置已确定的待决问题，编号并给出推荐。问题多时分组呈现，帮助用户一次回答；不能把依赖未决答案的问题提前混进本轮。轮数不设上限，但每一问都应能说明会改变什么决定。

问题用普通语言，必要技术词立即解释。推荐必须是明确、可接受或可修改的建议；“是/按建议”能够对应明确选择。对开放创作给出有实质差异的情境或结果，不只给表面同义的选项。

回答后的动作：
1. 更新唯一的当前摘要中的确认项、委托项及新约束，移出已解决的未决问题；保留问题编号方便对应。旧结论如需追溯，归入历史并明确已由什么决定替代。
2. 检查与之前答案是否矛盾。发现矛盾时指出具体两项及影响，不自行挑更方便的答案。
3. 可查事实先查；未得到事实的分支保持未决，其他独立问题继续。
4. 重新展开下一层，直到结果性问题解决。

不要逼用户选择技术框架、目录结构或算法。其影响确实改变费用、部署、兼容或使用方式时，问可理解的结果取舍，由 Agent 提出技术方案。例：“必须断网可用，还是可以上传到云端处理？”比“用哪个数据库？”更有用。

## 用户不知道、跳过或改变方向

- 不知道：给对照情境或小样说明差异，再问偏好；不重复抽象问题。
- “你定”：界定委托范围，给推荐及理由，记录为委托决定，不写成用户亲选。
- “先跳过”：未决仍是未决；可以保存草案，但不把影响结果的未知隐藏在最终可执行版中。
- “别问了，先给草案”：遵守用户新指令，交付明确标注的待确认草案和阻塞项；启动指令只允许续接准备，不能把它当完整执行授权。
- 改方向：说明哪些确认项失效，重开受影响分支，保留仍有效的约束。
- 暂停：保存当前事实、决定、未决问题和下一步；恢复时不要求重答全部内容。

## 结束条件

下列信息足以让一个未参加访谈的人判断任务，且不存在会改变结果的隐含分歧时，才提出需求复述确认：

1. 对象、用途和预期收益清楚，能给出一个完整的典型场景。
2. 最终交付物、使用方式、必要规模和质量特征明确。
3. 必须项、可选项、明确排除项可区分；没有把建议当要求。
4. 材料、时间、预算、运行/交付环境和重要权限限制有依据。
5. 对关键失败、冲突和不可接受结果有处理约定；只覆盖真实相关情形。
6. 验收具有区分度：知道什么结果合格，什么即使“文件生成了”也不合格。
7. 已确认、用户委托、待执行时核查的事实清楚分开。
8. `more-than-yes` 的实质补充已被处理，用户确认当前复述准确。

“后续执行时核查的事实”可以存在，但须明确检查方法以及各结果对应的行动；若其中一种结果会改变用户目标、成本或使用方式，应现在调查或保留为需用户决定的阻塞项。

不是达到以上标题数量就结束：尝试用复述说明一个具体输入怎样变成预期结果。解释不通的地方就是要补的问题。也不是消除一切实现未知才结束：用户委托且不改变结果的技术决定由 Agent 承担。
