# Get Clear｜问清楚再改

这是 Easy Ask AI 中处理已有成果返修的 Skill。它既负责问清含糊的不满意，也负责把明确改动实际完成。**是否读取与是否访谈是两个决定：匹配本技能的返修先读取；读后按请求选择分支。** 不因“我已经知道怎么改”“只是一行”而绕过入口，也不为使用技能而增加用户确认。

**按语义识别反馈，不做关键词匹配。** 结合当前任务，只要用户在表达已有成果与期望有落差，就重新判断；不要求出现“修改”“不好看”或技能名。“差点意思”“拿不出手”“不像我要的”“太套路了”“看着累”“用起来别扭”“好一些，但没到那个感觉”“换个思路吧”只是不同领域的例子，方言、口语、反问和上下文中的简短否定同样按含义处理。本轮具体操作已明确、同一改向已获确认且没有新的未决反馈，或有可复现客观故障时直接修；自己的审美原因假设不算已确认。期望仍有多种解释才问。看似具体的建议或回答也要检查：其中的用词、指代、程度或隐含前提是否仍会导向不同改法；不能只因出现“少用”“调整”“保留”等动作就判为明确修改。已有原文和有效决定能消歧时直接沿用，否则按提问方法辨别那一处含义。用户的情绪不等于审美答案；与当前成果无关的抱怨、引用他人评价、纯故障和讨论技能不一律套成访谈。

## 先判断这次回答解决了什么

返修不是从“不满”直接跳到“修改”。每轮只更新用户实际回答的部分，在当前任务上下文保留以下短判断，不要求用户填表或新增永久文件：

| 当前知道的内容 | 下一步 |
| --- | --- |
| 不满存在，但所指仍不清楚 | 用原作的一处具体表现辨别含义 |
| 已知道嫌哪一处，但想要的替代效果仍有分歧 | 继续辨别那一处想保留什么、变成什么；不先改成自己的默认样式 |
| 访谈已得到替代效果与保留范围 | 输出详细需求理解报告，请用户核对是否符合想法、是否完整；补充或否定则继续追问并更新报告 |
| 用户明确认可本次报告；或原本就是没有未决含义的明确小改 | 读取执行分支，在当前回合完成并核验 |

例如“我说的是那圈光，看着刻意，状态标记有用”只定位了不满，并保留状态标记；它没有选择去掉光、减弱光、换颜色或改背景。结合当前画面问仍未定的一处差别。相反，原本就明确要求“去掉背景渐变和光晕，保留深色、布局和状态标记”可直接执行。若这是正在进行的访谈回答，则记入本次报告，连同其他已澄清内容交用户核对，再实施；不能把一个具体回答当作批准全部改向。具体色值、代码与工具由 Agent 选择，不要求用户承担实现工作。

**访谈的默认闭环：主动追问 → 详细需求理解报告 → 用户补充/继续追问并更新报告 → 用户明确认可 → 实际修改。** 报告在当前对话供用户阅读，写清目标、反馈含义、拟改与保留范围、边界、未决事项及检查方式；按实际需要充分展开，不用一句“明白了”代替。补充偏好、回答某一题或沉默不算认可；还觉得不够就继续，不限定轮数。报告准确和完整由用户核对，事实错误由 Agent 发出前自行校正。用户明确改变流程或停止时遵从；原本明确的小改不强行启动此闭环。

## 读后只走适用分支

**每次效果反馈都重新判定当前阶段，包括提问工具返回的用户答案。** 之前读过、执行过或确认过方案，不代表下一次含糊否定已处理；旧确认只保留已经明确的维度，不能据此选择新反馈的含义。比如早先确认“像工作人员自然招呼”，成稿后又说“收得太狠、读着干”，仍须辨别本轮所指，不能把它直接翻译成“加回招呼感”并修改；不以宿主是否开启新回合判断。连续否定、全选缺点或无法回答仍走下表的含糊分支，先完成完整访谈的必读材料，再按访谈指引加载恢复页；恢复页不能替代完整访谈。制作多稿以后或领域技能正在执行时同样适用。

选择分支后实际打开该行列出的必读文件，不能只凭入口摘要开始问或改。已安装依赖、知道其名称或能复述规则，均不等于已读取对应文件。

含糊反馈当前要完成的是澄清：先读本分支材料，再为下一问取足够的作品证据。已有截图或原文能支持当前一问时，直接使用，不先搭预览、调浏览器或跑整套制作调研。只有这问确实依赖尚未观察到的动态状态才补看运行效果；工具受阻时使用可得证据并说明缺口，不让环境重试替代访谈，也不清理其他任务的进程或窗口。

含糊分支按顺序读取：先读依赖说明并实际读取 `grilling`、`more-than-yes`，再单独读完整访谈和提问方法，最后按需读反复否定的恢复页。这样先取得通用方法，再按本任务的访谈规则使用；依赖的默认问卷和推荐答案格式不是本流程的输出格式。各文件分别返回，输出截断则补读缺失部分；文件名出现或读取命令执行过不代表正文已完整获得。已经读过且仍有效的材料可复用，无需为了顺序重读整包。

本技能负责澄清，不替代领域执行方法。匹配的领域技能也按当前宿主列表读取完整入口：例如 UI 观察与返修时，已安装的 `ui-done` 仍须读取；`frontend-design` 的审美建议或某个参考片段不能代替它的完整流程。未安装的可选领域技能不要求补装，缺失能力如实说明。

**效果方向不等于明确操作。** 仅说“更亲切、庄重、清爽、有吸引力”等期望，即使指出原稿某种不适感并要求修改，也仍进入含糊分支；事实齐全、文字很短、你已想到改法，都不能替用户确认表达方式。直接执行须有指定的具体操作/替换内容、此前已确认的完整改向，或明确委托你决定的依据；“请改好”本身不是这种委托。先按用户实际提供的依据判定，再读对应材料，不先预告要直接改写。

| 当前请求 | 在编辑前读取 | 随后行动 |
| --- | --- | --- |
| 原本是明确小改，具体位置与操作已明确，没有未决含义，也没有正在等待认可的访谈报告 | [执行与精确修改](references/execution.md) | 跳过访谈与访谈依赖，在本回合实际修改并核验指定差异 |
| 只要求继续落实已确认方案，本轮没有新的未决反馈；或明确委托你决定本次改向 | [执行与精确修改](references/execution.md) | 沿用已确认边界，完成并检查，不重复确认 |
| 关键分歧已问清、偏好已补齐，但还未认可本次完整报告 | [完整访谈第 4 节](references/interview.md#4-问清楚的判据与确认) | 核对原始条件、修正后发出详细报告；用户补充或否定时继续追问并更新，再请核对；明确认可后才实施 |
| 仍有会改变结果的含糊期望，或建议/回答中的关键含义未清 | [完整访谈](references/interview.md)和[提问方法](references/questioning.md)；按[依赖说明](references/dependencies.md)检查并读取 `grilling`、`more-than-yes` | 结合原作一次问一个主要问题，问清后提交详细报告供核对，用户认可后进入执行分支 |

先读当前作品和相关上下文；已知事实不重问，不能观察到的内容不假装看见。混合“好点了”、否定、参考和改法时仍判断剩余期望是否明确，不能把方法线索当成效果已确认。

含糊分支的共同底线：不把猜测改法当作用户决定；不先写整篇新稿或制作新版本绕过确认；复述保留用户所指的对象、行动和阶段；用户已回答的内容沿用。用于辨认单一差别的临时对照按提问方法处理，与编辑业务原件、交付新方案区分。进入该分支必须读完整访谈及其指定材料，不能只凭本页摘要直接开始问或改。

明确分支不需要加载 `grilling`、`more-than-yes` 或整套访谈。精确修改保留无关字节、编码和换行；不能用“我会修改”的最终答复代替实际动作，也不能只凭工具自述宣布完成。

访谈后准备修改时，核对用户是否已明确认可当前报告，或已明确改变本次流程并授权直接实施。仅指出哪里不满意、补充偏好或回答一个具体操作都不等于认可报告。找到依据后读取执行说明并落地，不能把“我已想到办法”当成依据。整篇改写按执行说明双向核对：原材料中仍需保留的信息是否都写到，成稿中的条件和承诺是否都有同样范围的依据；发现自己的错漏当轮修正。

## 宿主安装与首次核验

用户明确要求安装或接入时，先读取[通用宿主接入说明](references/host-integration.md)，按当前宿主提供的能力和可核实版本调查，不套用另一宿主的路径。完整安装应保留本 Skill 的所有文件。用户只要求安装时不改宿主持久规则；要求接入但未说明作用范围时，完成只读调查后只问项目级或用户级等决定性范围。已在当前可信上下文明确的授权可沿用。本 Skill 的普通业务调用不构成新增全局或项目规则的授权。

首次明确调用时，经宿主提供的 Skill 列表、调用来源或当前会话的实际文件来源确认安装目录后，只在该目录查找 `.easy-ask-ai-host-setup*.md`，读取包含本 Skill 自有开始/结束标记且 Skill 字段匹配 `get-clear` 的记录。结合当前宿主实时信息核对 Host、Scope 和有效规则载体；不能只按文件名、修改时间、版本号或“最新”选记录。没有匹配记录、记录缺失/不可读或多个记录矛盾时，按无可信当前记录处理，只做不影响当前业务的轻量只读核对；不要扫描其他目录或因此延迟本 Skill 已明确的任务，尤其是精确小改。若要翻查大量配置或外部版本资料才能确定规则机制，先完成业务，再把接入事实标为待查。记录不修改宿主规则、不授予权限，也不能证明加载或行为通过。完整安装/接入、更新或撤销时，按[接入说明](references/host-integration.md)读取状态记录模板、更新并回读核验；不可写时先完成业务并如实标为未保存。日常轻量核对不做全盘哈希；完整接入时记录安装包文件指纹、规则片段及活动自有区段/原生条目的指纹或可比较副本。实际内容改变时使受影响证据失效；版本号相同不证明内容相同。宿主没有可靠 Skill 列表、读取记录或新会话检查方式时，按证据层级报告未知/待验证，不凭模型自报升级状态。

## 边界与交接

- 同一对话已读当前版本且分支规则仍在上下文时可沿用，不为了每一轮重复读取；改为另一分支时读取相应材料。
- 同一次模糊返修中的局部操作与整体改向一同进入报告，认可前不实施；另一个独立、原本明确的小改仍可直接执行，不借局部授权重做全部。
- 纯技术故障先调查报错，不进入效果访谈；普通问答、引用别人的评价或讨论/维护技能本身，不当成业务作品的返修。
- 默认留在当前工作区、当前任务完成返修。只有用户要求交接给另一对话时才转为 Prompt Ready。
- 本包不授予新的数据读取、付费、发布或全局修改权限。用户明确要求与宿主权限优先；不保证读懂所有审美，也不能从技能正文强制不可见的宿主入口。

安装与入口排查见 [README](README.md)。文件存在、宿主列出、实际读取和行为有效分别核验；隐式触发不能用事后“做对了”代替读取证据。
