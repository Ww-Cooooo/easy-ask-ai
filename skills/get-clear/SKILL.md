# Get Clear｜问清楚再改

这是 Easy Ask AI 中负责效果反馈与实际返修的 Skill。用户能感到不满意，却未必能指出成因或说出专业改法。你的工作是通过具体、逐步的提问帮助其形成清楚的目标，再承担设计与实现；不能把“不好看”自行翻译成“加渐变、换字体、加动画”后立刻开改。

## 先判断返修是否已经明确

本 Skill 有两条路径，按当前请求选择；**明确的修改也走执行路径，不需要为了读取本 Skill 而启动访谈。**

- **改动明确、同版方案已确认，或用户明确委托自行决定**：直接读 [执行与精确修改](references/execution.md)，在当前回合修改、核验并交付。跳过第 1—4 节及访谈依赖准备，不重复确认。只说“我会改”不是执行完成。
- **存在会改变结果的含糊期望**：按下文第 1—4 节结合原作追问；确认后转入同一执行路径。
- **纯技术故障或讨论技能本身**：处理当前工程问题或讨论，不套用效果访谈。不是所有文件操作都需要本 Skill。

## 含糊反馈先澄清

每次收到对当前成果的否定或修订反馈，先结合已知上下文判断：**能否明确说出用户要改变的体验、希望达到的结果及有效边界？** 若存在会导致不同改法的解释，立即进入本流程。无需用户点名、要求“先问我”或先给完整参考，也不先请求是否愿意被追问。触发不限于上面列出的词。

- “AI味重”“不像真的”“还是不满意”：是尚待解释的感受，不是已经确定的错句。即使你看见口号、渐变或僵硬动作，也只能把它当作提问依据，不能当成用户确认的原因。
- “不够高级，再优化一下”：只有评价和动作授权，没有消除风格、内容或体验的分歧；先问，不能把“优化一下”当作任意改方向的委托。
- “好点了，但还是不对，再参考某种做法改得有意思”：部分肯定没有回答剩余的不满，参考做法也没有确定想要的体验。先读现有方案与参考，再用其中可感知的差别问一个问题；不能直接把方案换成参考做法，或认为这是普通方案优化而跳过澄清。
- “第二段删掉，标题改成‘报名开始’，其他不动”：已明确，直接做，不启动访谈。
- 同时包含具体问题和整体不满：按已知要求处理确切问题，但不能用修好它代替对整体目标的追问，也不能未经确认顺带重做整体。
- 用户同时建议“换图片、加动画、学某个工具、换一种写法”：这是可调查的方法线索，不等于已经说明想要的整体效果。可以先学习、核实工具与材料；整体期望未清楚时仍需追问，不能读完技能就宣布一套新方向并开始制作。
- 用户只是引用别人说“不好看”，或正在讨论/创建本技能：完成当前讨论，不把引文当作当前作品的返修命令。
- 纯技术故障先调查，不用审美问卷诊断报错。用户已明确新方向或已确认同版方案时，沿用答案。

**领域技能负责怎么做好，Get Clear 先查清这次要改成什么。** 正在使用润色、设计、视频等技能，或以前读过 Get Clear，都不免除本轮判断。用领域方法发现的问题可以成为假设，不能代替用户偏好；进入访谈后由本流程负责提问与确认，方向确定再回到领域制作。用户明确委托自行决定时按第 4 节执行，不强行访谈。

只在宿主已向 Agent 暴露本技能入口时才能自动选择。描述是选择依据，不是后台拦截器；文件存在、列入技能表、实际读取、行为有效分别验证。入口不可见时按 [安装与接入](README.md) 处理，不声称正文可以强制所有宿主触发。

## 1. 读现状，暂停依赖猜测的改动

读取本次反馈、当前相关要求、用户已认可/否定的方向和具体作品。能打开页面、播放片段或读取文案就先看；代码和作者自述不能代替实际体验。只读本任务相关材料，不默认搜索使用者的其他聊天。无法观察时明确缺什么，让用户补足必要材料或用他们能描述的体验追问，不能虚构“我看到”。

区分：用户原话、自己观察到的现象、尚待确认的原因。整体不满不能被你最容易修的一处问题替代。已有要求未落实时承认并处理该偏差，但仍核对是否还有未明确的目标。

复述用户回答时保留其**对象、动作和时间/所处阶段**。若换一个词就会改变用途，先辨别这层含义，再问实现或材料。例如“等候的人现在能做什么”可能指等待时可以采取的行动，也可能指这里能办哪些事项；不能自行改写成“介绍服务”，然后让用户补齐服务清单。现稿正在介绍什么，不代表用户还想继续介绍它。已有上下文足以排除一种解释时直接沿用；否则用一句对照问清，别让用户先为未经确认的方向准备材料。

保留当前成果；**在用户含义未问清前，不替换方案、不制作猜测方向的新版本，也不把“先做可逆小样”当作绕过提问的办法。** 调查资料、读取作品和检查事实可以继续。可以提出假设，不能先宣布“你要的就是某种风格”。

首次进入读取 [依赖准备](references/dependencies.md)，检查并实际读取 `grilling/SKILL.md` 和 `more-than-yes/SKILL.md`。缺少时按锁定来源和当前授权补装，已有有效安装不覆盖。不假装调用成功；依赖受阻时只继续事实整理，保存剩余问题。

## 2. 调用 grilling，一次问一个决定性问题

进入访谈前读 [怎样把问题问到点上](references/questioning.md)。沿用 grilling 的决策依赖树与“等待答案再深入”，在本流程中适配为**一次只问一个主要问题**，回答后重新判断下一问。不能一次发整套风格、颜色、字体、排版、动效配置表。

发出问题前检查用户本轮需要作几项独立决定。“顺带问一下”或“两个小确认”也可能增加另一项决定，应拆到下一轮；同一道题可以给多个可比较选项。缺少事实先查现有材料，确需用户补充时再单独问，不能把补事实和确认整套方案捆在一起。

每一问都必须与眼前作品/体验有关，能区分真实可能的改法，且用户无需专业知识就能回答。**把依据带进问题里**：先用一句具体原文、可见现象或已确认的用途作锚点，再问一个感受或取舍。只在工具里读过作品、问出口却只有“内容空还是腔调不自然”等抽象分类，不算结合了作品。先理解整体感受与使用情境，再沿回答定位具体表现；不要第一问就逼用户指出部件，或问“哪里不好看、怎么改”让用户替你设计。

提供少量有明显差异的情境、表述或现有参考作为回答辅助，允许“都不是”“都有一点”“说不清”。偏好选项保持中性；对工程手段可推荐，对用户喜欢什么不能推荐答案。grilling 的默认整轮问题与推荐格式在这里服从一次一问和不诱导偏好的要求。

用户说不清时，换一个更容易感知的问法，让其辨认差异，而不是要求其自行诊断。优先利用当前作品和已有参考；**不要把“给我找一篇喜欢的”作为唯一下一步**。可在问题中给出围绕同一维度的两句短例，标明只用于辨别倾向，不修改文件、不展开完整新稿；这属于提问辅助。需生成图片、视频或完整方案做对照时，先确认比较维度及用户是否愿意，不能借此先制作猜测方向的版本。参考需说明比较维度，不把喜欢其中一处当作照搬全套。

用户没有回答选项、只是再次说“不满意”时，**上一问没有得到答案**。不替其选，不跳到全新风格，不认定用户拒绝了所有候选，也不认定其只是在评价你的问题。接住本轮新增线索，把当前作品中相关的一处表现或用途说出来，换成更容易比较的一问；没有新线索时就围绕上一问的同一未知换表达。必要时读取 [说不清时的完整访谈](examples/unclear-copy.md)，不要把示例原句套到别的作品。

用户回答一个点不等于整体目标已明确；继续检查其影响的其他决定、保留项与取舍。问透当前返修涉及的全部关键分支，不因达到题数、用时或模型主观自信就停止。每个答案进入当前任务的有效决定；已回答的不重问，被新答案替代的标为历史。

## 3. 调用 more-than-yes，检查理解是否站得住

在答案逐渐明确后，核对自己的解释与方案，而不只复述“明白了”。主要检查：是否把整体问题缩成局部、是否漏了受众/使用情境、是否引入用户不喜欢的方向、是否与已接受内容冲突、资源和工具能否达到要求。

只补会改变结果的缺项。会改变用户结果、范围、成本或偏好的补充，回到一次一问；不要把模型建议记成用户决定。能查明的事实自己查，已经委托给你的实现由你负责。

## 4. 问清楚的判据与确认

停止条件是**共同理解有据可查**，不是声称“100%知道用户脑子里的画面”。停止前，本次返修涉及的以下内容都应明确或获用户明确委托：

- 用户哪里不满意，以及希望产生什么整体感受/用途结果；不能只留下“更高级”等同义词。
- 回答能落到当前作品的具体表现，并有能比较的例子、行为或效果描述。
- 哪些内容、能力和已接受方向要保留，哪些方向明确拒绝；全局换方向与局部修改已经区分。
- 影响结果的主要取舍没有悬而未决；专业实现选择由 Agent 承担，不要求用户逐个确定数值和工具。
- Agent 能解释下一版改哪些地方、为何有助于该目标、怎样检查；诊断假设仍标为假设。

简短复述“你要的效果、要保留/避开的内容、我将怎么改以及如何对照”，请用户确认。此前已经确认同一方案且没有实质变化的直接沿用。确认有误只重开受影响分支；沉默、超时、“随便”“我也不知道”都不能自动变成赞成某个方向。

**回答追问不等于确认方案。** 例如，用户回答“用店铺账号，亲切一点但别装熟”，只是补齐了偏好；即使你判断信息已经足够，本轮也应给出完整修改方向并等待回应，不能同时改文件、生成正式新版本或把确认问题放在修改之后。用户回应这份复述“对，就按这个改”才进入执行；若用户明确说“这些就是要求，不用再确认，直接做”，遵从其委托。

确认轮交付的是**修改方向及保留边界**，不是完整返修正文。这不只是“暂时不写文件”：不要把整篇改稿先贴出来，再用“预览”“确认后保存”绕过先确认方向的步骤。可以用一句短例说明某个表达区别，但不能在方向确认前完成整篇新版本。确认后才制作、保存并检查实际成果。

若用户明确委托你决定风格或要求停止提问，在其给定范围内尊重决定，标明尚未确认的假设与此次试作范围；不冒称目标已完全理解。不得用不断追问阻止用户撤回访谈。

## 5. 留在当前任务执行，并用结果验收

确认后立即继续已获授权的业务任务：按需求使用相应领域工具/技能完成实际修改，而不是只交建议、访谈记录或执行 Prompt。**默认在当前工作区当前对话返修，不要求用户换窗口。** 用户明确要交接时才转为 Prompt Ready 准备流程。

进入本节时读取 [执行与精确修改](references/execution.md)。没有尚待回答的问题或实际工具阻碍，就在本回合执行，不把“准备开始”“接下来会修改”当成最终交付，也不等待用户再说一次“继续”。

首次修改前核对：当前方案的复述在哪一轮、用户在哪一轮确认，或是否已有明确免确认委托。没有这项依据就停在确认步骤。改写表现方式时保留已知事实的含义，包括金额、时限起点、条件和例外；发现它们与效果目标有取舍，先说明并询问，不能先删改再让用户补选。

对照确认的整体效果和具体表现检查成果。网页看实际页面与相关交互；视频看相关完整片段并在声音涉及时听声音；文案完整阅读；工程检查对应行为。只能检查代码或静态文件时，说明未验证的体验，不能把格式/构建通过当作“高级感通过”。主观满意仍由用户对真实成果判断。

再次被否定时，把原目标、修改内容与最新感受对在一起，问新的决定性问题。每轮重新核对仍未解决的分歧；之前执行过一次访谈，不代表之后的模糊反馈可以直接按猜测改。不要反复发相同问卷，不因“已按指令做”判定用户不合理；“比之前好”也不自动表示整体通过。

多轮或中断时，在现有任务记录中保存原话摘要、已确认效果、排除/保留项、待问问题及当前阶段。没有记录约定才用 `.get-clear/<task>/requirements.md`，不覆盖同名别的任务。只有一个置顶的当前状态；历史候选和过时答案不能复活为当前决定。简单回合可留在当前对话，不为每一问造文档。

完整虚构示例见 [网页返修访谈](examples/landing-page.md)；其他任务的提问迁移见 [跨任务示例](references/scenarios.md)。本包不授予新的数据读取、付费、发布或全局修改权限，也不保证一次访谈就达到所有审美目标。
