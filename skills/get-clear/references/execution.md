# 执行并核对真实改动

本页用于已明确的返修、用户确认后的实施和明确委托自行决定的任务。此时不再启动 grilling 或要求同一方案二次确认。

## 当前回合完成动作

先读目标文件/页面和已有边界，确定要改变的部分与保留部分，再调用实际编辑工具。可以简短告知正在做什么，但“我会先检查再修改”只能是进度说明，不能作为这轮最终答复。读文件、拟方案和生成替换规范也不等于修改已落地。

完成前检查：用户要的改动是否已保存到指定位置；实际差异是否在范围内；需要的业务结果是否核验。已确认且工具可用时，不把执行留给下一回合，不要求用户再说“请继续”。确有缺失输入或工具故障时，说明具体阻碍及已完成部分，不假装成功。用户只要方案时仍只交方案。

## 小范围文本替换

“只改这一行、其他文字和格式不动”包含换行符、文件末尾是否有换行、空白及原编码标记。视觉上读起来相同不够；读取修改前内容，修改后比较实际差异。优先使用能限制替换范围的编辑工具，或本包的精确替换脚本。

对一个已确认的文字替换，推荐使用 [edit_text.py](../scripts/edit_text.py)。它只处理 UTF-8（可带 BOM）或带 BOM 的 UTF-16 文本；不处理 Word/PDF、二进制、未知旧编码，也不自动猜测目标文字。Python 3.10+，仅标准库。

该脚本通过临时文件替换目标，保证范围是文本主数据流；不保证硬链接关系、NTFS 附加数据流、显式 ACL 或所有其他文件属性。任务要求保留这些属性时，使用能保留它们的宿主工具。本脚本的变化检查也不是任意并发写入下的事务锁。

1. 从真实文件读出待替换原文，选择足够唯一的完整片段。只改标题时可带上已观察的行尾来避免误匹配相似标题；JSON 中用 `\n` 或 `\r\n` 表示实际行尾，不混用。
2. 在任务允许的临时位置创建 UTF-8 JSON 规范，例如：

```json
{"old": "## 导出", "new": "## 导出记录", "expected_matches": 1}
```

3. 调用脚本，路径按本机已安装位置确定，不把示例占位符直接执行：

```text
python <get-clear目录>/scripts/edit_text.py <目标文件> --spec <规范.json>
```

成功输出 `applied: true` 和替换数量、改前后摘要；脚本保持无关字节并回读验证。无变化时输出 `applied: false`，不能当作另一次新修改。匹配不到或数量不符时不写入，重新读文件定位原因，不改成无条件全文覆盖，也不简单重跑原命令。可在规范中提供读文件时取得的 `expected_sha256`，拒绝覆盖该次读取后发生的变化。

实际执行后，回读涉及的内容并核对用户要求；清理自己为这次调用新建的临时规范，不删除用户已有文件。脚本只确保指定替换准确，不判断这段文字是否符合用户意图。

没有 Python 时，用宿主原有的定点补丁/文本编辑能力，或保留原编码的字节读写，再核对差异。补丁工具也可能自动补上文件末尾换行；只检查补丁中写了哪一行，不能证明其他字节没变。修改前保存原始字节，比较实际结果是否恰好等于原始内容中的指定替换。未被 Git 跟踪的文件不会出现在普通 `git diff` 中，空输出不是通过证据。

**不要把 `Get-Content -Raw` 的结果直接交给默认的 `Set-Content`/`Out-File` 回写**：它们可能追加换行或改变编码；仅回读全文会漏掉这种差异。PowerShell 文本回写必须明确编码和是否附加行尾；不能靠删除所有尾部空白来修复，因为那些空白可能原本就存在。

若发现自己多加了换行或改了无关内容，依据本轮修改前的副本纠正自己的差异并重新核对；不要借机规范化整份文件，也不要覆盖在此期间出现的他人修改。

## 其他返修

较大文案修改核对完整含义和保留项；代码检查对应行为；网页和音视频使用各自制作与验收工具。结构化文档不能用本脚本直接替换容器中的任意字节。只检查过文本或代码时，不声称实际页面、声音或动画已验收。

最终答复报告已经完成的修改、可打开的产物和有意义的检查。没有待答问题、实际阻碍或用户限制时，不以将来时计划结束已授权的执行任务。
