# 执行并核对真实改动

本页用于已明确的返修、用户确认后的实施和明确委托自行决定的任务。此时不再启动 grilling 或要求同一方案二次确认。

执行前核对委托依据：只有用户明确把本次方向取舍及制作交给 Agent（如“这版你定，按你的来做”）才适用。“你觉得呢”“你比较懂”“你觉得怎样设计比较好”是征求意见，“你不要问我，我没有审美”本身是拒答或求助，都不能据此制作新版本。委托只对那一次产出有效；该产出被整体否定后失效，回到[完整访谈第 1 节](interview.md#1-读现状暂停依赖猜测的改动)，不继续沿用。详细判据与拒答路径见[第 4 节](interview.md#4-问清楚的判据与确认)。原本明确的小改与仍有效的已确认方案不受影响。

## 当前回合完成动作

先读目标文件/页面和已有边界，确定要改变的部分与保留部分，再调用实际编辑工具。可以简短告知正在做什么，但“我会先检查再修改”只能是进度说明，不能作为这轮最终答复。读文件、拟方案和生成替换规范也不等于修改已落地。

用户给出文件路径时，依据宿主实际权限检查目标是否可读写；路径在当前工作区之外本身不是访问失败的证据。没有实际权限限制或访问结果，不凭目录差异声称“无法访问”并结束。权限确实禁止、文件不存在或工具不可用时，说明已核实的具体阻碍，遵守限制，不绕过权限。

完成前检查：用户要的改动是否已保存到指定位置；实际差异是否在范围内；需要的业务结果是否核验。已确认且工具可用时，不把执行留给下一回合，不要求用户再说“请继续”。确有缺失输入或工具故障时，说明具体阻碍及已完成部分，不假装成功。用户只要方案时仍只交方案。

## 小范围文本替换

“只改这一行、其他文字和格式不动”包含换行符、文件末尾是否有换行、空白及原编码标记。视觉上读起来相同不够。完成依据只能是精确替换脚本成功回读，或保存的原始字节经过指定替换后与实际文件逐字节相同；标题出现一次、文件摘要存在、回读文字或补丁显示一行改动都不能替代这项核验。

对一个已确认的文字替换，Python 可用且符合下述范围时，默认使用 [edit_text.py](../scripts/edit_text.py)，不自行改成未经字节核验的文本回写。它只处理 UTF-8（可带 BOM）或带 BOM 的 UTF-16 文本；不处理 Word/PDF、二进制、未知旧编码，也不自动猜测目标文字。Python 3.10+，仅标准库。

**先确认编码，再判断原文是否存在。** 不要把未知文件固定按 UTF-8 解码，然后因零匹配就让用户纠正文案。先检查原始字节的 BOM：`EF BB BF` 为 UTF-8，`FF FE` 为 UTF-16 LE，`FE FF` 为 UTF-16 BE；无 BOM 时严格验证 UTF-8，无法验证则停止猜测编码。读取工具可自动识别 BOM，但手工调用 UTF-8 解码器不会自动处理 UTF-16。出现乱码、异常空字符或零匹配时，先核对编码和真实内容。包内脚本会按这些编码规则读取，可直接处理已确认的原文，无需先用错误解码结果拒绝任务。

该脚本通过临时文件替换目标，保证范围是文本主数据流；不保证硬链接关系、NTFS 附加数据流、显式 ACL 或所有其他文件属性。任务要求保留这些属性时，使用能保留它们的宿主工具。本脚本的变化检查也不是任意并发写入下的事务锁。

1. 从真实文件读出待替换原文，选择足够唯一的完整片段。只改标题时可带上已观察的行尾来避免误匹配相似标题；JSON 中用 `\n` 或 `\r\n` 表示实际行尾，不混用。
2. 使用宿主文件写入能力，在任务允许的临时位置创建 UTF-8 JSON 规范，例如：

```json
{"old": "## 导出", "new": "## 导出记录", "expected_matches": 1}
```

3. 单独调用脚本，路径按本机已安装位置确定，不把示例占位符直接执行。创建规范、调用脚本、清理临时文件分开操作；不要拼成同时包含读写、运行和删除的长 shell 命令：

```text
python -X utf8 <get-clear目录>/scripts/edit_text.py <目标文件> --spec <规范.json>
```

成功输出 `applied: true` 和替换数量、改前后摘要；脚本保持无关字节并回读验证。无变化时输出 `applied: false`，不能当作另一次新修改。匹配不到或数量不符时不写入，重新读文件定位原因，不改成无条件全文覆盖，也不简单重跑原命令。可在规范中提供读文件时取得的 `expected_sha256`，拒绝覆盖该次读取后发生的变化。

实际执行后，回读涉及的内容并核对用户要求；清理自己为这次调用新建的临时规范，不删除用户已有文件。脚本只确保指定替换准确，不判断这段文字是否符合用户意图。

调用失败时先读返回原因，区分命令构造错误、工具缺失和真实权限限制；不绕过权限或执行策略，不把失败调用当成已修改。没有 Python 或需要使用其他获准编辑方式时，**在修改前另存原始字节**，按已确认的编码和唯一片段生成预期字节，再编辑、回读实际字节并计算两者是否完全相等。原始副本必须在后续检查时仍可取得；上一条失败命令中的变量不能当作已保存副本。

补丁工具也可能自动补上文件末尾换行。使用补丁或原生编辑后也必须完成上述比较；不因脚本失败就降级成只回读文本后宣布完成。未被 Git 跟踪的文件不会出现在普通 `git diff` 中，空输出不是通过证据。发现额外差异时先修正自己的变化，再比较；尚未取得相等结果就明确检查未完成，不能声称“其他格式不动”。

**不要把 `Get-Content -Raw` 的结果直接交给默认的 `Set-Content`/`Out-File` 回写**：它们可能追加换行或改变编码；仅回读全文会漏掉这种差异。PowerShell 文本回写必须明确编码和是否附加行尾；不能靠删除所有尾部空白来修复，因为那些空白可能原本就存在。

若发现自己多加了换行或改了无关内容，依据本轮修改前的副本纠正自己的差异并重新核对；不要借机规范化整份文件，也不要覆盖在此期间出现的他人修改。

## 其他返修

整篇改写前，先从**原稿和简报两处**提取会影响实际参与、使用或交付的条件，逐条记清原句及处置：保留、用户已明确变更，或真实冲突待解决。可在当前任务的工作记录中简短列出，不为小改另造文档。不只依赖自己刚整理的摘要；简报未重复原稿某条条件，不代表它被撤销。想让表达更轻松，也不是取消资格、携带物、费用、产出或隐私条件的授权。没有明确变更依据就保留其含义，调整表达方式；无需把所有介绍性语句逐字复制。

较大文案修改完成后，从本次原稿、简报和有效用户决定中列出仍须向读者传达的事实及限制，再逐项在保存后的成稿中找对应表达。按任务核对受众/适用对象、用途阶段、条件与例外、时间地点、费用名额及操作方式；不是每个任务都需要全部字段。未改错不等于没遗漏：只存在于内部简报、从文风猜得出来或被其他信息替代，都不算已经告诉读者。也不能为了语气更自然把条件改成可选、承诺或全新事实。发现缺漏时在本轮补回并重新通读，不把可自行发现的遗漏交给用户指出。

再反向检查成稿中的事实性说法，尤其“无需、免费、全部、一定、可以、必须”等条件和承诺：原始材料或用户决定能否支持同样的范围和强度？词义接近不是等价。例如“无需购买”不推出“不用携带”或“现场提供”，“无需经验”不推出“无需准备”，“分享自愿”不推出“没有分享环节”。没有依据的扩大表达改回已知条件；确有冲突且会改变结果时再问，不用顺耳的近义词填补未知。核对正向保留和反向依据两遍后，才报告检查完成。

代码检查对应行为；网页和音视频使用各自制作与验收工具。结构化文档不能用本脚本直接替换容器中的任意字节。只检查过文本或代码时，不声称实际页面、声音或动画已验收。

最终答复报告已经完成的修改、可打开的产物和有意义的检查。没有待答问题、实际阻碍或用户限制时，不以将来时计划结束已授权的执行任务。
