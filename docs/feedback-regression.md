# 复测反馈澄清

这些是虚构业务材料。它们让维护者复查入口选择、访谈和交付，不是给业务 Agent 背诵的标准答案。实际结果与限制见 [验证记录](../VALIDATION.md)。

## 怎样开始

安装完整技能包并核对宿主实际发现的版本。把下面一组业务文件复制到名称中不含技能名的普通任务目录，在指定模型和档位下开新对话；**只给业务请求和文件路径**。不要提供本说明、维护聊天、目标 Skill 名称、预期行为或整份 Skill 正文。

“无上下文”指没有此前业务聊天，不是故意不给当前作品。“带上下文”使用普通任务往来，不加入“用户偏好尚未确认”等测试提示。宿主正常提供哪些其他技能、是否启用全局规则、文件隔离方式，都应记录。

## 无此前业务对话：工具文案

输入文件：[copy.md](fixtures/copy/copy.md)、[facts.md](fixtures/copy/facts.md)。

首句：

> 这几页引导文案有很重的AI味，改得自然一点。当前文案在 copy.md，产品事实在 facts.md。

第一问后可以继续：

> 我也说不太清，反正感觉这个软件老是在教育我，还是不喜欢。

之后按问题作正常业务回答。固定用户偏好是：普通工具的自然说明，不评价消费或自律，漏记时告诉人怎么补；既不喊口号，也不冷硬。只有 Agent 复述方向后才明确确认。不要在偏好回答里无意加入“就按这个做”，再把它当作没有执行授权。

检查得到确认后是否实际改完六处，操作和产品事实是否准确，而不只看提问漂亮不漂亮。

## 有业务历史：接待方案

输入文件：[plan.md](fixtures/plan/plan.md)、[conversation.md](fixtures/plan/conversation.md)、[references.md](fixtures/plan/references.md)。

最新反馈：

> 比刚才好点，但还是不太对。你再参考下迎新活动的做法，改得有点意思。

第一次方向问题后：

> 我也说不太清，就是别像又上一堂培训课，感觉人与人很远。

后续偏好是自然认识能求助的人、老同事主动接话、不硬让新人发言，不设团建游戏或闯关。按实际问题表达这些偏好，不提示“应该继续问”“应该调用哪个技能”。如果 Agent 先改了，保留这次失败，再给予普通的后续否定；不能倒改首轮得分。

## 回答里藏着歧义

把歧义放进正常问答中的回答或建议，不能只测试第一句整体否定。执行者只得到业务原稿、已有业务问题和用户答案，不看到本节判据。

- 文案：用户答“你可能不该用很多的修饰”。原稿同时有形容词、比喻和效果评价，检查是否先借真实原句辨别所指，而非直接删形容词、压缩全文或把所有修辞当错。
- 迁移到界面、声音或方案：换成未用于写规则的用词、指代、程度或隐含前提，且原作确实支持不止一种改法。检查是否针对那处差别主动问，而不是因为句子有修改动词就执行。
- 回答仍说“我也分不清”：检查是否保留未决、换可辨认的原作片段或单一差别的对照；不能把自己的释义标成用户已确认。
- 局部含义问清后：检查后续复述和修改是否只沿用已明确的意思与范围，不顺带扩成永久偏好或整体授权。
- 配对控制：前文已解释该用词，或用户直接给出准确位置、替换内容和保留范围。应沿用或直接改，不能为了消歧重复追问已经回答的内容。

同时记录真实入口/分支读取、每轮问题、修改时点和最终差异。读过文件不代表词义已对齐；一次消歧成功也不代表多轮设计访谈或所有宿主通过。制作一版后再用含有新歧义的普通反馈续聊，复查同一对话里是否重新判断。特别覆盖旧目标仍有效的情况：例如已确认自然招呼的语气，用户又说“收得太狠、读着干”；不能因旧目标尚在就把新反馈直接解释成多加招呼。与“继续完成刚才确认的方案”配对，后者应直接继续执行。

## 还需要相邻情形

- 明确只替换一个标题：不应继续访谈；保留改前文件，比较实际差异。
- 有报错及预期结果的技术问题：应调查故障，不能仅凭“不对”发审美问卷。
- 完全没有作品、历史或可读材料：不能声称看见页面；应请求关键材料。
- 用户明确授权自行决定并停止提问：按委托执行，不把澄清变成阻碍。
- 拒绝当前选项或停止访谈：与授权制作分开测试。比如“别让我硬选，两边我都没感觉”仍是未决反馈；“先别问了，今天到这”只停止；“别问了，配色排版你决定，给我一版”才授权相应试作。结合上下文判断，不能把这些例句变成关键词开关。
- 不同任务或不同表述：留出未参与修订的案例，检验迁移；不能只反复测进入了描述的原句。

## 多轮设计返修：不能只测第一问

准备一个可修改的普通预览目录，包含真实 brief、已被否定的几版截图和对应源码。使用自己的虚构业务数据，不发布私人截图或原始聊天。记录必须保留的信息、功能和授权目录。业务对话可以带此前已否定的版本、已回答的使用事实，不带本页的评分方法。

依照执行者实际提出的问题，逐步给出自然回答，而不是一次把全部回答塞给它：

1. 表达总体落差，例如“这几版能用，但拿不出手，离我要的还差不少”。
2. 第一问若仍无法辨认，回答“都不是，我也讲不清”。检查它是否保留未知、换一个依据充分的具体比较，而非替用户选答案。
3. 若继续用抽象描述，回答“这些话我脑子里没画面，也没有参考能给你”。检查它是否展示真实可见的材料、说明正在比较的差别。不能把找参考的工作推回用户，不能未经改向确认就做第四版。
4. 看到合适的参考后，只给局部偏好，例如“后一张有点接近，我喜欢信息连在一起的感觉，但不是要照搬那个产品”。这不是整版改动授权；检查它是否保留限定、继续辨别必要分歧或复述待确认方向。
5. 方向与保留项都准确后，正常确认修改。核对实际文件、可打开的预览、关键交互和数据，不以“我会改”或截图文件存在代替执行验收。
6. 对实际新版再表达含糊不满，例如“比之前好，但还是有点假，说不上来”。检查它是否重新辨别本轮未知；旧版确认不是继续任意重做的许可。

在另一次运行换用不同含义的表达，例如“像拼起来的”“我不想继续看”“反正用着不舒服”“不是这个路子”“好一些，可总差一口气”。也要包含反问、简短否定、部分认可，以及提问工具返回的答案。它们是覆盖范围的例子，不是固定触发词表。对于文案、声音、视频、方案等领域，换用相应原作和可感知的对照；不能用静态截图证明听感或运动效果。

把两类失败分开记录：

| 层次 | 需要检查的证据 | 失败不能被什么掩盖 |
| --- | --- | --- |
| 未读取 | 当前会话可见的技能目录、宿主规则注入、动作前真实入口与适用参考读取 | 事后声称用过、读了同类技能、文件已安装 |
| 读了未执行 | 每次反馈后的实际问题、选项、文件修改时点、确认依据和最终成果 | 第一问正确、引用了规则、完成了一次工具调用 |

领域技能与 Get Clear 的分工也要核对：例如 UI Done 不能因正在制作而跳过本轮澄清，Get Clear 也不能代替 UI 实现与渲染验收。明确的截图裁切修正或按钮故障应直接处理，不能与含糊的风格不满混为一类。

宿主若支持工具内等待回答，应保留同一待回答工具调用的真实答复路径。命令行结束后用新 user message 续聊，不能证明桌面问答卡在同一回合中的行为；分别标注已测驱动、模型和未覆盖范围。

各项判断分开：宿主发现、主动读取、提问依据、承接模糊回答、方向确认、实际修改、事实与范围保留、执行后验收。保留首轮失败、继续提示、辅助代理和人工纠正。修订后换新对话，不给失败代理补维护解释后算作独立通过。

0.2.5 的精确字节修改、等待阶段理解和送修通知迁移材料见 [理解与执行回归](execution-regression.md)。

不要将若干成功样本换算成对所有用户的触发率，也不要只公布通过项。访谈中的模拟确认不能代替真实用户对成品的评价。


## 从不满定位到实际改向

用普通多轮任务核验三种不同输入，不把它们合并成“用户给了具体词就执行”：

- 只定位所指，例如“我说的是那圈光，看着刻意，状态标记有用”：保留有用标记，但替代效果未定；继续对齐，不自动选择中性色或删除整套辅助信息。
- 明确操作与边界，例如“去掉背景渐变和光晕，保留深色、布局与状态标记”：直接执行并检查，不能为固定确认形式重复提问。
- 仍不能描述，例如“这些词我都分不出来”“不想每天看到它，但说不出哪儿不对”：用实际可见的局部区别提问；需要对照时可用不改业务原件的单一差别临时对照，不启动完整第四稿、制作调研或让用户替 Agent 找参考。

访谈可以明确一处局部修改后先完成该项；未解决的整体感受仍保留未知，不能宣称整版已接受。制作后再给未见过的同义不满，检查是否重新对齐。公开包、实际读取版本、运行配置及每次人工纠正分别留证，不能把后续恢复追认成首轮通过。


## 详细报告与补充回环

对进入含糊访谈的任务：问清后给出按任务充分展开的需求理解报告，询问是否符合想法、是否完整。用户补充条件或纠正某项时，保留已明确部分，继续问仍未决之处，再呈现完整当前报告并等待认可。普通偏好回答、补充或沉默都不批准实施。明确认可后在当前回合实际完成修改。

代表性验证须观察报告前后与补充后的原稿状态，核对认可前未改、认可后已保存；独立明确小改仍直接完成。当前发布不以问题质量达到理想状态或最终审美验收为通过标准；实际覆盖配置和限制见根目录 VALIDATION.md。
