## 已确定的故障层次

0.2.5 曾出现一次 Luna / max 不读取 Get Clear、直接正确修改文件的情况。它的初始技能列表包含完整描述和正确路径，因此不能把故障解释为没有安装或宿主完全没发现。两次新的同版对照都读取并完成，也不能用它们覆盖原失败。

本轮候选 C 的22个新会话均核对了实际模型、思考档位和初始技能列表：完整候选描述可见，未被截断。发生漏读时，可见行为是模型直接进行文件编辑，没有读取技能正文。**这是选择阶段的漏用；可见记录不足以确定模型内部为何这样选择。**

## 候选尝试与保留的失败

- A：缩短入口，把完整访谈移到参考文件，明确“先读，再决定是否访谈”。Luna / max 的明确修改仍漏读，产物字节正确。
- B：把面向读者的 Markdown 标题、句子、段落修改放在描述前部。Luna / max 仍漏读，产物字节正确。部分描述尾部被宿主截断，但正向匹配条件仍可见，不能把截断断言为原因。
- C：将描述压缩到147个字符，保留所有作用范围和排除条件；访谈方法只迁移位置与相对链接，没有删除。Luna / max 再次漏读，还增加了文件末尾 CRLF。

没有再通过反复改描述、只展示成功重试的方式宣称修复。以下矩阵统一使用冻结后的 C；A、B、旧版对照和显式调用另计。

## 全档位新对话矩阵

精确修改的原件包含 UTF-8 BOM、混合 CRLF/LF、行尾空格且无文件末尾换行。由维护者按原始字节的唯一替换独立比较。含糊反馈核对是否读取、是否提出结合现稿的问题、是否在方向确认前修改文件。

## 显式入口与完整流程

另一个新 Luna / max 对话收到相同的明确修改任务，但点名 `$get-clear`。它读取入口及执行说明，调用精确修改脚本，维护者的独立字节比较通过。这仅证明本次显式调用能工作，**不能充作隐式触发修复**。

Sol / medium 与 Luna / max 的含糊反馈对话继续完成了模拟业务流程：用户选择“自然认识能帮忙的人、第二天敢求助”，排除点名轮流发言、游戏和闯关；代理先复述方向，获得确认后在当轮保存方案。两稿均保留90分钟、同楼不扰办公的安排，联系人与路线保留待团队核实，没有把接待同事当成所有事项负责人。事实文件未改。维护者回读检查了实际文件，没有追加纠错指令才让它们落盘。这里验证的是方案文件交付，不是现实活动效果或真实用户审美验收。

## 证据边界与处置

测试使用 Codex 子代理，`fork_turns=none`；实际模型和档位与上表一致。宿主仍提供正常全局技能、规则、记忆和共享文件系统，不是操作系统隔离实验。部分代理查看了相邻测试方案；Luna / low、xhigh 还查到前轮虚构迎新参考。因此这些结果可用于检查此次入口选择，不能夸大为完全隔离、从未见过同类材料的泛化证明。全部冷启动结果在完整流程回复前冻结，未用后续修改覆盖初轮状态。

结构校验通过；原有精确修改脚本本轮未修改，其单测不替代模型行为证据。没有读取隐藏推理，也没有把代理对自身行为的解释作为根因证明。
