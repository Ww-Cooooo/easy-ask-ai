# 接入与排查

## 安装位置与独立使用

本仓库根目录是 Easy Ask AI 套件，不是 Skill 入口。将 `skills/prompt-ready`、`skills/get-clear` 中所需的完整目录安装到当前宿主实际确认的技能位置；两者均自包含，不要求保持仓库中的相邻关系。安装路径、用户/项目适用范围和发现方式由宿主、版本及部署确定，不能套用另一实例的结论。

先从当前宿主提供的技能列表、配置、帮助/状态或文件读取能力确认有效路径、启用状态、项目级冲突和旧会话快照，再读取对应入口。保留本地定制；有同名安装时核对来源和差异，备份后合并，不覆盖未知修改。细节见[通用宿主指南](host-integration.md)及各自随包的[Prompt Ready 接入说明](../skills/prompt-ready/references/host-integration.md)、[Get Clear 接入说明](../skills/get-clear/references/host-integration.md)。

## 在你自己的工作流明确接入

希望日常返修先读取 Get Clear 时，可选择随包的[规则片段](../skills/get-clear/assets/agents-snippet.md)；准备任务时也可选用 Prompt Ready 的[规则片段](../skills/prompt-ready/assets/agents-snippet.md)。按当前宿主的真实载体、格式和用户授权范围接入。只安装 Skill 不改规则；显式或普通业务调用也不授权新增项目级/用户级规则。接入与撤销步骤见通用指南和对应 Skill 的独立说明。

只依靠 Skill 描述、手工给模型全文或显式命令调用，不能证明宿主会在正常业务中隐式选择。若在领域技能中使用 Get Clear 逐条澄清，应先完成它的提问与确认，再回到原领域流程继续制作和验收；避免同时启动相互冲突的两份问卷。用户已明确要求逐条询问时，领域流程的批量问题或直接试样不能覆盖它。

明确的文字替换、只改标题或已确认的返修采用 Get Clear 短执行分支，跳过访谈及访谈依赖准备；当前回合实际保存并核验。精确文本任务比较实际字节差异，不能只凭空白的 `git diff` 或“已修改”自述通过。该分支不要求为普通代码故障启动效果访谈。回答追问只补齐需求；除非用户明确委托直接执行，仍须复述整体修改方向并等确认。每轮只保留一个待决定项。

## 证据与业务排查

1. **Skill 已安装**：完整文件在确认的目标位置。
2. **宿主已发现**：真实列表列出名称、有效路径和状态。
3. **规则已写入**：正确文件区段或原生条目存在。
4. **宿主已加载**：新会话宿主状态证明规则进入会话；`loaded` 配置诊断不证明模型读取或业务表现。
5. **模型已读入口**：真实工具记录证明模型在动作前读取了对应入口。
6. **正常业务入口/行为已检查**：任务没有点名 Skill；记录实际第一步及后续关键步骤，并核对可见结果。
7. **用户已接受**：只按用户对实际结果的评价记录。

检查 Get Clear 的业务表现时不能只看第一问：继续用正常输入观察 Agent 是否承接“说不清”“还是不满意”或具体偏好，是否利用现有材料，以及是否在方向确认前擅自改稿；确认后还要核对实际返修成果。另用明确小修改检查它是否无端进入长访谈。隐式测试不点名 Skill，也不预先塞完整正文。发现但没选择时，检查描述、调用策略、同名冲突与上游技能路线；已经读取却直接改时，检查规则冲突、问答与动作，不只继续堆触发词。修改后复核受影响的层次并保留历史失败和未验证范围。

## 从旧安装迁移

`prompt-ready` 名称与 `.prompt-ready/` 任务目录保持兼容。Get Clear 不加载 Clear Feedback；使用者决定替换旧技能后，只移除旧的活动技能目录，保留需要的备份，并定向更新指向旧入口的项目规则。不要删除历史业务需求，也不要把备份放进仍会扫描的技能根目录。

已经运行的聊天可能保留旧技能清单或规则快照。宿主支持重载时按其机制刷新；否则新开会话或显式读取新入口，准确区分磁盘状态、宿主加载与模型实际读取。移除文件不能证明旧会话已清除内容。

## DeepSeek 一直思考，却没有回答

先看停止原因。`max-tokens` / `max_tokens` 表示单次输出到达上限；它不等于账户欠费、请求限流或网络中断。思考也占输出额度，可能在可见答案开始前用完。`low` 表示较低思考强度，不保证一定在某个小额度内结束。

2026-10-20 核对的官方接口说明中，Anthropic 兼容接口使用 `thinking.type` 开关和 `output_config.effort` 档位；`thinking.budget_tokens` 被忽略。带工具调用的历史思考需要按接口规则回传，不能靠随意删除历史字段来“修复”。见 [思考模式](https://api-docs.deepseek.com/guides/thinking_mode/) 与 [Anthropic 接口说明](https://api-docs.deepseek.com/guides/anthropic_api/)。

排查顺序：

1. 核对实际宿主、provider、模型、思考档位、单次输出上限及停止原因。官方 Harness 与同名社区 TUI 不是同一个程序；配置文件中的意图也不等于实际发出的参数。只记录必要元数据，不打印密钥、请求头、业务正文或思考全文。
2. 检查是否由外层测试脚本或旧配置设置了过低的 `maxTokens`。本项目旧测试的 8,192/16,384 上限是维护者设置，不是模型或官方 Harness 的默认值。本轮受控复测采用 65,536；这是测试条件，不是所有任务都应采用的固定推荐。提高上限可能增加消耗，保持宿主已有授权和预算边界。
3. 检查流程是否提前展开了尚无答案的全部方案。Prompt Ready 应先问当前结果性问题，等回答后再推进；已委托的实现细节由 Agent 调查。详细完整的最终 Prompt 可分段保存，写完再整体核查。
4. 中断后先看需求状态及已保存文件，保留失败记录，判断是续接当前阶段、调整已确认配置还是重开执行上下文。不要连续盲发“继续”、静默切到 `off` 后仍称原档位通过，或把半份文件交给执行者。

模型输出存在波动。一次成功不能证明档位永远不会耗尽额度；改变配置后通过，也不能单独证明 Skill 降低了成本。实际案例、用量和仍未证明的部分见 [验证记录](../VALIDATION.md)。
