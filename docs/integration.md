# 接入与排查

## 安装位置与独立使用

本仓库根目录是 Easy Ask AI 套件，不是 Skill 入口。将 `skills/prompt-ready`、`skills/get-clear` 中需要的完整目录安装到宿主实际发现的根目录。两者均自包含，依赖辅助脚本和锁定文件各随包提供；无需保持仓库中的相邻关系。

用户级安装可跨工作区发现，但项目级同名技能、禁用配置、旧对话快照和宿主列表限制可能影响本次实际使用。先查看当前技能列表中的路径与启用状态，再读文件；不覆盖使用者的未知修改。

## 在你自己的工作流明确接入

需要日常返修先读取 Get Clear 时，使用随包的[宿主规则片段](../skills/get-clear/assets/agents-snippet.md)。它覆盖明确修改和含糊反馈：先读入口，再决定直接执行还是访谈。规则可经使用者同意合并到项目或用户级指令，安装文件本身不会自动写入。完整操作与撤销步骤见[宿主接入说明](../skills/get-clear/references/host-integration.md)。

只安装 Skill 与接入宿主规则是两种运行条件。发布验证分别记录，不能用后者掩盖前者的漏选。`description` 提供匹配线索；`AGENTS.md` 可声明工作流要求，这是 Codex 官方介绍的配合方式，仍需实际运行检查。[官方说明](https://developers.openai.com/blog/skills-agents-sdk)

在领域技能中接入时，先由 Get Clear 负责此次访谈和确认，再回到领域技能完成制作与验收；不要同时运行两份相互冲突的问卷。用户已明确要求逐条问时，领域流程的批量问题或直接试样默认不能覆盖它。

明确的文字替换、只改标题或已确认的返修采用 Get Clear 的短执行分支，跳过访谈与访谈依赖准备；当前回合实际保存并核验。精确文本任务比较真实字节差异，不能只凭空白的 `git diff` 或“已修改”自述通过。该分支不要求为普通代码故障启动效果访谈。

回答追问只补齐需求；除非用户明确委托直接执行，Agent 仍需复述整体修改方向并等用户确认，不能改完再补问。每轮只保留一个待决定项，小的事实问题也不要与方案确认捆在一起。

## 四层证据不能混淆

1. **文件存在**：完整包可读。
2. **宿主发现**：实际列表包含正确名称、路径与启用状态。
3. **读取入口**：正常任务没有点名技能，Agent 仍在合适时读取它；记录是否已接入宿主规则。描述选择题、手工给全文、命令显式调用不能证明仅凭描述的隐式选择。
4. **实际行为与结果**：读后问到点上、等回答、达到确认条件才制作，并检查成果。只读文件或宣布“使用了”不足以证明有效。

检查第 4 层时，不止看第一问：继续输入正常的“说不清”“还是不满意”或一个具体偏好，观察下一问是否承接答案、利用现有材料，以及是否在方向确认前擅自改稿。确认后还要看到实际返修成果。隐式测试不在任务里点名 Get Clear，也不把完整正文预先塞给模型；另用明确修改检查是否无端进入长访谈。

若发现但没有选择，检查描述、调用策略、同名冲突与上游领域技能路线；若已读仍直接改，检查当时的规则冲突、问答与动作，不只继续堆触发词。修改后用正常任务复核对应层次。

## 从旧安装迁移

`prompt-ready` 的名称与 `.prompt-ready/` 任务目录保持兼容。Get Clear 不加载 Clear Feedback；使用者决定替换后，移除旧的活动技能目录，保留需要的备份，并定向更新指向旧入口的项目规则。不要删除历史业务需求或把备份放进仍会扫描的技能根目录。

已经运行的聊天可能仍带旧技能清单或已读全文。宿主支持重载时刷新；否则新开聊天或显式读取新入口，准确区分“文件加载”与“宿主自动选择”。不能从磁盘移除一个目录就声称清空了所有旧会话上下文。

## DeepSeek 一直思考，却没有回答

先看停止原因。`max-tokens` / `max_tokens` 表示单次输出到达上限；它不等于账户欠费、请求限流或网络中断。思考也占输出额度，可能在可见答案开始前用完。`low` 表示较低思考强度，不保证一定在某个小额度内结束。

2026-10-20 核对的官方接口说明中，Anthropic 兼容接口使用 `thinking.type` 开关和 `output_config.effort` 档位；`thinking.budget_tokens` 被忽略。带工具调用的历史思考需要按接口规则回传，不能靠随意删除历史字段来“修复”。见 [思考模式](https://api-docs.deepseek.com/guides/thinking_mode/) 与 [Anthropic 接口说明](https://api-docs.deepseek.com/guides/anthropic_api/)。

排查顺序：

1. 核对实际宿主、provider、模型、思考档位、单次输出上限及停止原因。官方 Harness 与同名社区 TUI 不是同一个程序；配置文件中的意图也不等于实际发出的参数。只记录必要元数据，不打印密钥、请求头、业务正文或思考全文。
2. 检查是否由外层测试脚本或旧配置设置了过低的 `maxTokens`。本项目旧测试的 8,192/16,384 上限是维护者设置，不是模型或官方 Harness 的默认值。本轮受控复测采用 65,536；这是测试条件，不是所有任务都应采用的固定推荐。提高上限可能增加消耗，保持宿主已有授权和预算边界。
3. 检查流程是否提前展开了尚无答案的全部方案。Prompt Ready 应先问当前结果性问题，等回答后再推进；已委托的实现细节由 Agent 调查。详细完整的最终 Prompt 可分段保存，写完再整体核查。
4. 中断后先看需求状态及已保存文件，保留失败记录，判断是续接当前阶段、调整已确认配置还是重开执行上下文。不要连续盲发“继续”、静默切到 `off` 后仍称原档位通过，或把半份文件交给执行者。

模型输出存在波动。一次成功不能证明档位永远不会耗尽额度；改变配置后通过，也不能单独证明 Skill 降低了成本。实际案例、用量和仍未证明的部分见 [验证记录](../VALIDATION.md)。
