# 0.2.0 历史验证

这是 0.2.0 发布时的记录，保留当时的失败与未验证项；当前结果见 [0.2.1 验证记录](../VALIDATION.md)。

版本：0.2.0。日期：2026-10-20。以下记录区分文件检查、宿主发现、主动选择和实际行为，不把其中一项代替其他项。

## 本轮改动与检查依据

Easy Ask AI 包含两个独立安装包：保留 Prompt Ready 的任务准备及同工作区交接能力，新增 Get Clear 处理模糊效果反馈并继续当前任务返修。Get Clear 根据本轮需求和获准核查的业务回合重新编写，没有沿用 Clear Feedback 的方法正文。

本轮采用 Skill Improve 核对原意、独立运行条件和业务行为。特别检查：

- 没有点名技能时能否主动选择；已经读取后是否真正先问。
- 用户说不清时能否换一种具体问法，而不是反复要求专业规格。
- 用户提出工具或写法建议时，是否仍识别尚未明确的整体期望。
- 问清并确认后是否实际修改；明确修改是否会被误拦成访谈。
- 包离开作者聊天和原仓库相邻目录后，是否仍有完整方法、依赖来源及使用说明。

用户授权的本地历史核查发现了“未主动澄清，先选设计解释”和“已经读过技能，仍未澄清就制作”两类情况。这些案例只作为诊断依据，不构成同条件的新旧版本对照。原始对话、提取记录和私人路径没有放入本套件；公开示例均为虚构。

## 官方 DeepSeek Harness 实测与修订

本轮使用实际安装的 `@deepseek-ai/dsh@0.2.1-rc.2`，通过 `deepseek-official` 请求 `deepseek-flash`，不是用其他模型扮演 DeepSeek。配置由启动补丁指定，会话记录也标记了同一 provider/model；未取得服务端底层型号或路由证明。

测试在 Windows、PowerShell 7 中进行。关闭默认项目指令和自动扩展技能根目录，向 Harness 提供已安装的两个目标技能与 `grilling`、`more-than-yes` 共四个入口；模型按需实际读取包。各新会话没有本项目开发聊天，业务材料均为虚构。隔离是会话与配置层面的，文件范围靠任务约定，**不是操作系统沙箱**；不能据此推断包含所有全局技能时的选择率。

### Get Clear：从模糊反馈到返修

- **发现的问题一：** 第一份维修提醒案例中，模型先主动读技能、问问题，但把用户回答偏好当成执行确认，直接修改。该轮未通过确认步骤。
- **针对性补充：** 明确“回答追问不等于确认方案”，给出容易混淆的例子；首次修改前必须能指出哪份方案已被确认，或哪条用户指令明确免确认。补清金额、时限起点、条件和例外不能在改写中丢失。
- **发现的问题二：** 新的桌游邀请案例会等待确认后返修，但把两个小问题捆成一轮。补清“小确认也属于独立决定”，与方案确认分开。
- **最终包的新会话复测：** 虚构书屋闭馆通知，用户仅说“没感觉、有点不对劲”，未点名技能。模型主动调用 Get Clear 并读两项依赖；先问期望感受，收到“选不出来、别让人白跑”后改问主要受影响的人群。再完整复述修改方向和保留事实，等待“对，就按这版方向改”才写入并回读。四轮中，确认前没有修改正文。
- **成果核对：** 闭馆日期、重开时间、读书会取消且不补场、无需另办取消、到期书顺延免逾期费、书箱满后带回并改日归还的含义均保留；把闭馆和读书会取消前置，去掉原有公文套话。此为文本与约束核查，不代表真实读者接受。

最终复测请求采用 `high` 思考档，单次输出上限 16,384 token。另一个未点名技能的明确标题替换案例没有启动访谈，正文只改指定标题；但 Harness 编辑工具把文件末尾 CRLF 规范为 LF，因此**不声称该例逐字节仅改标题**。

### Prompt Ready：准备与同工作区交接

初次旧衣改造活动案例的 `high` 请求分别在 8,192 和 16,384 单次输出上限下中断；其中一次普通“继续”能恢复提问，但后续仍耗尽额度。`low` 的新会话也在 16,384 上限中断。`off` 能开展访谈，却出现过多专业实现选项和无充分核查的可行性断言。该活动案例未完成完整交接，也没有验证实物做法。

据此补充两点：专业实现交给 Agent 调查和设计，用户只决定影响结果、成本和使用方式的取舍；可行性陈述必须区别已核查事实与经验建议，条件不足就列验证动作和失败分支，不能用肯定措辞代替证据。软件案例不证明上述实物做法已变得可靠。

另取未参与上述改写的离线器材借还工具案例，以 `off`、16,384 单次输出上限验证最终包。测试用户需要单人 Windows 命令行工具，只用 Python 标准库，保留借还历史、支持部分归还，坏记录不得当空记录处理。用户逐轮确认业务边界，并明确“两次各还一件属于正常操作”及将实现细节委托给 Agent。这些澄清属于正常用户输入，不能宣称模型无需用户参与就独立定好了全部业务规则。

准备会话完成需求访谈、依赖检查与补充判断，保存 `requirements.md`、约 22 KB 的 `execution-prompt.md` 和 `start.txt`，明确引导同一工作区新会话；准备阶段未生成业务代码，原清单未改。复述时的“先借一件却分两次各还一件”，以及 Prompt 中未经核查的日期和错写的示例人物，由维护者以测试用户身份指出后才得到纠正。因此这一结果是**经过用户式复核的完整交接**，不是无人监督一次正确；专业细节提问仍偏多，不能宣称相关问题已被规则完全消除。

随后启动一个不带准备聊天历史的新 Harness 会话，工作区保持相同，只发送 `start.txt` 与文件访问边界。执行者读取保存的材料，实际生成 Python 程序、中文说明和测试，自行修复测试语法及历史累计显示等问题，最终 **24 项自动化测试通过**。执行中触及测试驱动器设置的 24 步上限；保留中断记录、放宽驱动器上限，以普通“继续完成原任务”恢复同一执行会话，没有人工改代码或提供修法。

维护者另外运行 **19 次独立命令操作**，核对：超库存与非法数量拒绝写入、两次部分归还成功且第三次报错、备份等于上次有效文件、既有流水前缀不变、含逗号和引号昵称正确保留、损坏记录不改写且不覆盖备份、错误清单禁止写入。全部符合确认的业务边界，原始器材清单哈希未变。执行会话后续收尾未改变接受独立核对的程序。此结果证明该案例的准备与同工作区执行链路完成，不代表所有领域的技术方案都已验证。

### 失败、用量与适用范围

上述失败没有被删除或算为通过。另有一次凭据引用未接通和一次测试启动补丁缺少必填配置；修正宿主接线后再运行，没有向业务模型披露密钥或开发诊断。

本轮全部官方 Harness 探索、失败、修订复测和执行续接合计有 132 个返回用量的模型步骤。按宿主原始字段分别累计：`inputTokens` 137,741、`cacheReadTokens` 3,033,216、`outputTokens` 152,101、`cacheWriteTokens` 0；`totalTokens` 3,323,058。这包含维护测试开销，不能当成一次日常使用的消耗；未取得实际账单，不估算费用。

结果只覆盖这些任务和记录的配置。不能据此保证高/低思考档都能完成准备、所有任务一次成功，或 Get Clear 在任意宿主中 100% 自动触发。原始会话和本机路径未放入公开包；公开报告只保留虚构业务概要和结果边界。
